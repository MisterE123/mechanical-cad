# Guarded Windows Blender capture: bounded development checks

This public technical summary describes a development candidate, not a general installed Windows release qualification.

The candidate wires registration, asynchronous bundled preparation, immutable backend selection and live currentness through guarded Windows owners. External/raw Windows Python selection remains closed. No environment, preference, model or manual-cache override replaces the identity checks.

A packaged launcher uses the current-user OS-registered ApplicationData LocalCache provider. An ordinary unpackaged launch uses KnownFolder. Bounded launcher ancestry, original process handles, creation times, live state and unchanged package registration bind selection. Query failure, recycled ancestry or uncertain handle retirement fails closed. NTFS identities, DACL, bundle pins, DLL origins, child/descendant lifetime and cleanup checks remain active.

Historical focused checks included installation/enabling, guarded gear replay/export, save/reopen and owner cleanup in a controlled native test environment. Results belong to their tested candidate, not an unbuilt later revision. These checks used a 240-second timeout; the default 60-second workflow gap remained outside that qualification. Separate pure-suite fixture failures and native capability/solver failures were also documented; no all-green full-suite claim is made.

Current platform confidence must come from fresh tests of the published revision, including actual GUI Apply/Cancel, Undo/Redo and installed-package behavior. Private source-transfer details, machine paths, artifact hashes and executor-session narrative are omitted.
