# Dormant Windows transport integration

This development slice connects the existing file-backed Windows process owner
beneath the existing `SidecarJob`. It is **not Windows support, a release, or
permission to distribute a runtime**. Public Windows selection remains closed.
The immutable qualified Linux candidate and its evidence are not qualifications
of these new source bytes.

## Exact admission and authority boundary

Public `BackendSelection.capture` and `capture_bundled` reject unsupported hosts
before resolving preferences, environment or filesystem settings. Public bundled
capture also rejects a Windows policy on Linux. The raw bridge and ordinary
manual-path `SidecarJob` reject Windows before configuration or launch.

The explicitly named lower `_capture_windows_bundled_transport` constructor is
only a qualification seam. The finite source guard rejects any production caller
or alias. Its record grants no Ready status, installed setup policy, current
owner, receipt, typed result or permission to publish. Actual Part, Sketch and
Assembly owners still recapture through the unchanged public runtime boundary.
There is no environment variable, preference, model field or generated-constant
escape switch.

Registration is a narrower guarantee: the unchanged registration function still
resolves its package path and asks Blender for its extension cache with
`create=True` before setup rejects Windows. It does not start preparation/native
work or establish fresh authority. It is not a zero-I/O entry point. Moving that
check belongs to the separately reviewed automatic-cache work.

## One operation, one owner

The Windows worker stores its adapter before acquiring anything. It acquires one
existing shared bundle pin, fully re-verifies the exact materialized tree, checks
the captured descriptor and installed release/bootstrap/manifest bytes, and
validates retained local NTFS identities. It does not instantiate the Linux
operation owner or use its POSIX descriptor protocol.

Directory anchors deny deletion/rename. The direct interpreter, bootstrap and
private DLL/PYD files additionally deny write sharing and are rehashed through
retained handles. Other Python/source files receive full-tree manifest verification
under the shared pin; they are not individually retained against in-place writes.
This is trusted installed software and a cooperating same-user boundary, not a
sandbox against hostile same-user modification. Pathname `CreateProcessW` and
observed image paths are not executable-by-handle authentication.

The worker derives `SystemRoot` and `WINDIR` only from the bounded OS query. It
creates one `<cache>/.jobs/<32-hex-token>` directory outside the immutable runtime
and uses it for `TEMP`/`TMP`. These four values are the complete immutable child
environment. Per-operation directories do not enter stable selection equality.
No parent environment or Blender-global DLL policy is changed.

The existing Windows process owner owns all four files. Its API's initialization
hook records observational aliases only after each file is already owned. Before
creation, the validator checks four distinct identities and actual final paths
from those original handles, under the retained job directory. A bounded directory
listing additionally rejects missing, extra or substituted names. It never adopts
an enumerated file or reopens an output by pathname.

Constructor failure leaves the original pin and validation resources with the
adapter. Constructor success transfers ownership exactly once before start.
Only the original process owner closes those files/handles, then retires the
validation resources/private directory, and finally releases the pin. An
ambiguous close is never retried; validation and pin retirement remain blocked.
No successor, reset, fallback process or automatic operation retry is introduced.

## Completion and limits

One absolute deadline covers acquisition, verification, process setup and ordinary
execution. Post-return checks prevent a call that began in budget but returns late
from producing a successful response. Cancellation remains distinct from timeout.
OS calls are not preempted, so these bounds are not hard-real-time guarantees.
Cleanup has its own fixed, nonrenewable five-second admission/observation budget.
The original process owner's first failure or final-close entry establishes that
budget; a failed transient close is backdated to that exact close attempt. The
adapter never grants a second budget after internal start cleanup. Each cleanup
query, termination, resource close and validation-directory step has pre/post
checks. A callback that returns late (including the existing compound pin release)
is rejected; successful closes already observed stay recorded as closed. Expiry
latches uncertainty and stops subsequent cleanup calls, without retrying a close.

Root termination is insufficient. Both the retained root must be signaled and the
owned job must report zero active processes. A root that exits while descendants
remain is a failed operation; only its owned job is terminated. Both output
streams must satisfy their limits and be read under the original pin before
resource closure. The existing common JSON/envelope/exit-code rules remain the
same as Linux. No response becomes visible until cleanup is confirmed.

Cleanup uncertainty suppresses any response, wakes waiters, and leaves `done`
false while retaining the original owner. Existing synchronous execution
quarantines its lease; existing async owners retain their job/lease. The existing
restart diagnostic remains the recovery instruction. A lost or malformed export
reply after attempted start does not prove that no file was written.

The isolated child applies only the documented application-directory, System32
and explicit-user-directory DLL search classes before private imports, retaining
all five directory cookies through dispatch. Duplicate private DLL basenames are
rejected. This cannot authenticate Python's initial PE loads; actual mapped
origins and hostile CWD/PATH controls still need a genuine Windows host.

## Path and release gates still open

The present conventional Blender Windows cache is too long: the measured Alice
example produces 269 UTF-16 units for the longest final file and 285 for staging.
This slice deliberately uses conservative ordinary short DOS paths and inert
short-path test fixtures. It does not make the default install usable.

A separately reviewed automatic LocalAppData/MechanicalCAD/r cache, setup-worker
binding and registration ordering are mandatory before public activation. Full
final payload, installed-package, stage, job and actual stream path lengths must
be rechecked; the current eight-character tempfile stage suffix is not an API
promise. No short-name alias, junction, identity truncation or system long-path
policy modification is a workaround in this slice.

There is no authorized genuine Windows host or completed applicable redistribution
permission/source closure. Windows process/ABI/pin/DLL-origin gates, real native
CAD receipts, installed offline Blender first use, GUI, persistence, cancellation
and final exact-ZIP audit remain unrun. The mixed 54-stage aggregate contains
native execution and is a separate authorized gate.

## Evidence classification

New tests run the real `SidecarJob`, adapter and Windows process owner with narrow
fake file/Win32/clock leaves. The two filesystem-input seams replace only full-tree
verification and bounded input reads on Linux; their returned descriptors/bytes
still pass the real policy, manifest and retained-anchor checks. No fake CAD,
lease decision, process owner or response validator establishes success.

Finite source and test-harness inverses reconstruct every altered historical byte
before the existing guards run. Earlier fixtures, protected core hashes, the
129-runtime baseline and import/publisher/validator boundaries remain intact.
Pure controls are evidence of bounded composition and failure behavior only;
they do not discharge any Windows/native/GUI release gate.
